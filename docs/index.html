Most guardrails check the order. BOSS checks the permission path.

Size caps and allowlists verify what the agent is about to send. BOSS also enforces when sending is allowed: missing balances stay UNKNOWN, hard rule failures BLOCK, and a one-time EXECUTE token is required before Agent OS sees the packet.

“AI can make mistakes, act on outdated or hallucinated information, or send incorrect parameters — always verify before execution.” — Binance MCP Server documentation

Observe → plan → approve → act

One session shared by the web desk and the BOSS MCP tools.

Observe

Live ticker, depth, 1h SMA, Web3 trending boards, analysis reports.

Plan

Exact quantity, tick, min-notional sizing from Binance exchangeInfo.

Gate

Verdict CLEAR, UNKNOWN, or BLOCK with every rule visible.

EXECUTE

Single-use approval token (60s). No send without this phrase.

Send

Agent OS MCP places the order with stamped newClientOrderId.

Reconcile

Hash-chained receipts classify AUTHORISED vs FOREIGN / FORGED.

Fail-closed by design

VerdictMeaning
BLOCKA hard rule failed. No approval, no send.
UNKNOWNRequired fact missing (usually balances). Plan allowed; send refused.
CLEARGate open — you still must type EXECUTE.

HMAC order stamps

Every approved packet carries boss_<seq>_<mac>. Copying the prefix is not enough.

Scope burn

FOREIGN, FORGED, or MISMATCHED orders burn trade scope until you restore from the desk.

Default caps

100 USDT per order, 500 USDT per UTC day. Spot only. Withdrawals never.

Run the live desk

The full product runs locally — real Binance data, real policy gate, real MCP at port 8790. Clone, configure .env from the example, start, and open the desk.

$ git clone https://github.com/nrlartt/boss.git
$ cd boss && npm install && npm test && npm start
